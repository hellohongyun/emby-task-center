# 虚拟媒体库

管理后台的「虚拟媒体库」（`/login/virtual-libraries`）用于额外组织 Emby 已有内容。创建虚拟库后，从 Emby 实时搜索并选入影片；原有媒体库继续保留。虚拟库只保存关联，同一影片可以加入多个虚拟库，不复制文件，不修改原影片资料。

「已加入的内容」使用与媒体库一致的海报卡片网格，展示原影片海报、名称、年份和类型；缺图或加载失败时显示占位。卡片保留移除关联操作，类型不匹配时仍显示告警。

手机端将虚拟库列表与内容区上下排列，已加入和待选择内容均以双列海报展示。创建、编辑和反代表单按手机宽度排列，搜索、分页和操作按钮支持触摸；桌面端保留侧栏与内容区并排布局。这里适配的是管理网页，Emby 客户端界面仍由各客户端提供。

## 配置与使用

1. 在「系统设置」配置 Emby 地址和 API Key，作为管理端选片的信息源。
2. 打开「虚拟媒体库」，创建媒体库，选择类型、名称和排序，再搜索、勾选并加入已有内容。「从 Emby 选择内容」只查询电影（Movie）和整部剧（Series），不单独选择季、分集或其他类型；分页总数由上游按作品类型筛选后返回。电影库只允许电影，剧集库只允许整部剧，混合库允许电影和整部剧。客户端会根据库类型筛选内容，不兼容的条目会提示原因并禁止加入；需要混放时选择混合库。
3. 在同页的反代设置填写 **TgtoDrive 的 Emby 反代地址**，不是 TgtoDrive 管理台地址。留空时沿用系统 Emby 地址。
4. 设置独立监听端口（默认 `8097`），启用并保存。页面显示实际运行状态；端口被占用时保存失败，已有监听与已保存配置保留。
5. 在 Emby 客户端添加服务器，地址填写本服务的反代入口，例如 `http://服务器地址:8097`，继续使用原来的 Emby 账号登录。通过 HTTPS 部署时可将独立域名反代到该端口，需支持 WebSocket 升级。

初次安装不会自动启动新的监听；启用后自动随应用启动，配置、虚拟库和关联持久化到现有 SQLite 数据库。改变端口或停用会断开旧反代连接。

## 客户端媒体库顺序

在 Emby 的「媒体库顺序」中，可以把虚拟库与原媒体库混合排序。完整配置与 `Configuration/Partial` 保存请求仍原样交给 Emby。反代读取当前用户的 `Configuration.OrderedViews`，按客户端使用的 `Guid` 优先、`Id` 回退匹配顺序，再合并分页；兼容无连字符与带连字符的 GUID。后台排序仅作为未指定个人顺序时的默认顺序。

每次获取媒体库列表都读取最新偏好，不缓存旧顺序；偏好读取失败或超过 1.5 秒时回退默认列表。`MyMediaExcludes` 隐藏的库在普通列表中排除，设置页的 `IncludeHidden=true` 仍可列出，数量与最终结果一致。所有查询沿用客户端凭据。

## 首页与客户端发现

- Emby 4.10 首页使用 `HomeSections` 和 `Sections/{sectionId}/Items`，与侧栏的 `Views` 不同。反代按分区的 `SectionType=userviews` 识别媒体库行，合并虚拟库；继续观看、TTD 自有分区和其他分区保持原上游结果，不写死分区 ID。
- 首页分区分类按上游、用户及凭据隔离，最多缓存 60 秒，每次成功读取 `HomeSections` 刷新；只保存分区 ID 和类型，内容请求仍逐次鉴权。
- `/Library/MediaFolders` 和包含虚拟 ID 的批量 `/Items?Ids=...` 也能发现虚拟库。批量查询仅返回明确请求的原条目和虚拟库；上游错误返回无关影片时不会混入结果。带真实父范围的请求保持原处理。
- 这些是代理入口中的逻辑库，不会在 Emby 原服务建立物理媒体库或伪造磁盘目录。直接连接原服务仍看不到它们。

## 请求与数据行为

- 浏览接口额外展示虚拟库，库内内容返回原 Emby 条目 ID 和实时资料。搜索、排序、分页和递归剧集查询由虚拟库查询层与上游共同完成。
- 虚拟库的 CollectionFolder 在根列表和详情中均提供客户端需要的 `Subviews` 数组：电影库包含 `movies`，剧集库包含 `series`，混合库包含两者，并保留题材、文件夹子视图。此字段用于 Emby 客户端创建浏览标签，避免打开库时读取缺失数组报错。
- 登录、真实条目详情、播放信息、字幕、收藏、已看、进度和其他接口继续转发给 TgtoDrive。播放流保留 Range、状态码及外部直链重定向；WebSocket 双向转发。
- 类型校验只作用于本地虚拟库映射的新增和类型修改，不改变原媒体库或代理请求。前后端使用同一规则；批量加入包含不兼容条目时整批拒绝，避免部分加入。修改库类型与已有内容冲突时会提示并阻止保存；可改为混合库或先解除不兼容关联。
- 历史已保存的不匹配关联会保留并提示，不会自动删除或改库类型。已加入列表会说明可能在客户端不可见的原因；改为混合类型后刷新客户端，无需重新添加。
- 已保存的季、分集等历史关联继续保留；新增关联接口按 Emby 实际类型校验，只接受电影和整部剧。选中整部剧后，客户端仍通过原 Emby 条目浏览季、分集和播放。映射保存当前 Emby ID，以及上游可提供的 TMDB ID；不因同名或同 TMDB ID 自动合并多个来源。
- 本层不添加会员、并发或原有操作限制，也不替代原服务器的鉴权。客户端提供的 Emby 凭据原样传递；不会使用管理后台的 API Key 替客户端授权。
- 管理后台「移除」只解除关联；删除虚拟库只删除本地虚拟库和关联。客户端原有的真实媒体删除请求仍发送到上游，成功后清理对应虚拟关联；实际删片行为与权限由上游决定。
- 虚拟库封面使用首个有海报的关联条目；空库使用文件夹占位图。片名、简介和海报不提供单独覆盖。
- 直连 TgtoDrive 或原 Emby 的客户端不会看到本服务新增的虚拟库；必须连接新反代入口。

## 浏览性能

当列表明确只请求电影或整部剧（`IncludeItemTypes=Movie/Series`），并且当前映射全为作品条目时，递归参数不会触发读取全部季和分集，直接使用已映射的原 ID 查询，上游继续执行筛选、排序和分页。作品库的题材、年份等筛选默认读取作品资料；明确的季、分集、最近添加、继续观看及未限定类型的完整数量统计仍保留相应范围。历史文件夹等容器仍按原规则展开，避免遗漏其中内容。NextUp 直接查询真实映射父项，无需预先遍历所有分集。

这项优化不缓存媒体列表或播放响应，也不跨用户共用筛选结果。分集、详情与播放仍使用原上游条目。

## 原条目 ID 变化后的关联恢复

管理端读取「已加入的内容」时检查当前关联；客户端访问虚拟库内容、详情或封面时也会检查。检查按虚拟库、上游地址、用户上下文、认证凭据与映射身份快照隔离，结果短暂缓存 30 秒；同一上下文的并发请求共享检查，分页、筛选、Accept 等无关参数不重复检查。新增或移除映射后重新检查；自动修复得到的新快照可继续复用刚完成的检查。失败、鉴权拒绝与取消不作为成功缓存，等待方可用自身请求重试。没有明确用户的封面请求不会被当成某个显式用户请求共享结果。缓存只覆盖身份检查，正常查询仍逐次交给上游鉴权。仅虚拟库范围触发检查，普通媒体库、真实条目和播放请求仍直接转发。

新增关联会记录 Emby 提供的有效 TMDB ID。已存在的原 ID 仍有效且类型相同的旧关联可补齐该身份；原 ID 已失效且旧记录没有 TMDB ID 时不按片名猜测。原 ID 失效或指向其他身份后，仅当上游查询到**同类型、同 TMDB ID 的唯一候选**时更新本地关联，保持排序和虚拟库归属。候选为空、多个来源、上游读取失败或身份不能确认时保留关联，管理端显示具体原因并提供刷新、重新选片的提示，不静默删除。

检查最多等待 10 秒，超时保留关联并显示重试提示；不会在迟到的查询返回后补写关联。检查期间已移除或修改的关联不会被旧结果恢复或覆盖。数据库仅新增可空身份列，历史映射保留。此恢复只更新本地映射，不改变上游影片、权限、播放链接或合并策略；客户端检查始终使用原客户端凭据，不借用后台 API Key。

## Docker 端口

生产 Compose 使用 Host 网络，管理端口为 `12333`。启用虚拟库反代后，应用会直接监听后台设置的宿主机端口（默认 `8097`），不需要修改 Compose 或增加端口映射；只需确认该端口未被占用并在防火墙放行。

修改反代监听端口后重建容器即可生效。源码构建和隔离测试使用的 `compose.build.yaml` 采用桥接网络，才需要为反代端口增加与后台监听端口一致的 `ports` 映射。

## 验证范围

自动测试使用临时数据库和本地 Emby HTTP 夹具，覆盖 Emby 4.10 首页分区、Guid 排序、配置原样保存、批量发现、鉴权及透传。另使用实际 TgtoDrive／Emby 4.10.1.0 上游进行只读验证：首页媒体库行、Views、MediaFolders 均能合并虚拟库，批量虚拟 ID 不混入其他影片，并按上游已保存顺序排列；不修改远端用户设置。

官方 Emby 4.10.1.0 网页端通过本地验证代理连接上述真实上游，已验证两个虚拟库卡片可出现在首页「我的媒体」。这不是远端生产服务已经更新的证明。Emby 官方电视端、官方手机端、Forward、SenPlayer 和 Hills 的实际设备兼容性仍需分别验证，不能用上述 API 或网页验证代替所有客户端验收。
