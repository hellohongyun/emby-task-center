# 求片与补集

## 入口与流程

有效、未被冻结的会员在门户 `/` 的「求片」进入。管理员从侧栏「求片与补集」或手机端「更多 → 求片与补集」进入 `/login/media-requests`。

会员搜索 TMDB，核对作品名称、原名、年份和 TMDB ID 后选择作品。电影申请整部作品；剧集每条申请必须选择一个 TMDB 分季（包括有资料的 S00 特别篇），不提供整部剧或多季合并申请。不同季可分别提交。分季资料无法确认时不能提交，不根据片名猜测身份。

剧集可以选择「求片」或「补集」。补集必须填写缺少的集号或说明，例如 `E13–E16，缺少中文字幕`；集号说明为会员提供的信息，不代表系统已完成实际缺集核验。服务端重新读取 TMDB 资料确认作品及季号，不采用客户端自填的标题或年份作为身份。

第一阶段只提供申请、人工处理和结果查询。管理员自行寻找资源及入库，更新状态与反馈；申请不会自动下载、导入片源、创建任务或发送邮件，也不改变原媒体库存和播放器搜索行为。

## 记录与处理

会员页将「提交申请」和「我的申请」分开。提交按选择作品、填写申请、核对提交逐步展开；选择作品后收起搜索结果，需要更换时返回选片。切换页签保留当前页面内的表单草稿，刷新页面不会保存未提交草稿。提交成功后展示回执，可查看记录或继续申请。

管理页把状态筛选、作品／邮箱搜索、结果数和刷新集中在列表上方。手机上五种筛选同排展示。申请卡片突出片名、处理状态、电影或分季、申请说明和反馈，完整原名、TMDB ID、提交和更新时间可展开查看。长说明及反馈可展开阅读，收起预览不会改变保存内容。手机端处理申请使用底部面板，桌面端使用对话框，管理员可核对作品和申请说明后选择状态、填写反馈并保存。

管理员可在待处理卡片上直接「开始处理」，在处理中卡片上直接「标为已入库」。快捷操作保留已有管理员反馈，仍按记录版本写入并记审计；失败时不显示成功，不自动重复提交。需要修改反馈或其他状态时使用「处理申请」，面板用可直接点选的状态选项，并允许展开长说明，避免先滚过整段申请内容才能操作。

处理成功后在当前列表更新对应卡片；不再属于当前状态筛选的申请会移出列表，并显示作品和处理结果。保留当前搜索、分页及页面位置，只有需要补齐空页或显式刷新时重新读取列表；旧的在途列表读取不能覆盖已经确认的处理结果。

| 状态 | 含义 |
| --- | --- |
| 待处理 | 已提交，等待管理员处理 |
| 处理中 | 管理员正在处理 |
| 已入库 | 管理员确认已提供所申请内容 |
| 暂无法提供 | 当前无法找到或提供资源 |

会员仅查看自己的记录，可按状态和作品名称筛选、分页查看。在待处理或处理中可补充说明；结束的记录不能由会员修改。管理员可按状态、作品或会员邮箱检索，逐条更新状态和反馈。状态由管理员维护，不会仅凭检测到同一剧名就自动标为已入库。

## 已入库申请自动清理

只有「已入库」申请在保留满 7 天后自动永久删除。待处理、处理中和暂无法提供不参与清理。这里删除的是本项目的申请记录，不调用 Emby 删片接口，也不删除媒体文件、库存、会员或其他业务数据。记录删除后从管理员和会员列表消失；已有审计记录按原日志保留规则处理。

新记录从标记为已入库的时刻开始计算完整 7 天。仅修改管理员反馈不会重新开始计时；改回其他状态会取消本次清理计时，再次标为已入库时重新计时。管理员和会员列表展示保留规则，已入库申请的详情中可查看入库标记时间与预计删除时间。

升级时仅补齐时间字段，不在迁移过程中删除申请。历史已入库记录使用最近有效的更新时间作为保守起点；无有效时间的记录保留，不根据创建时间猜测清理日期。

生产运行时在启动后检查一次，之后每小时检查一次；满 7 天的记录在下一次检查时清理。每轮最多删除 500 条，积压记录分轮处理。清理在独立数据库事务内核对状态、时间并留下审计，已被重新打开的申请不因旧状态被删除。列表刷新后显示清理结果，过期页面对已删除记录的修改会被拒绝。

## 重复申请与编辑

同一会员对同一电影或同一剧集分季只能有一条未结束申请，求片与补集共用该限制。重复提交返回原记录，不覆盖原说明；需要补集时在原记录补充。不同会员可以申请同一作品，后台保留各自工单及反馈，不自动合并状态。已结束后可重新提交；管理员重新开启历史申请时，若同一会员已有未结束的同作品／季申请则拒绝。

管理员与会员编辑均检查记录版本。若另一方已修改，旧编辑会被拒绝并提示刷新，防止覆盖更新。提交、说明修改和管理员处理均记录操作审计。请求取消或超时仅表示前端不再等待，已开始的服务端写入可能完成，应刷新核对后再操作。

## 访问与保存

接口沿用独立的管理员、会员会话。会员权限在服务端动态检查，过期、冻结、停用和删除后的会员无法操作求片接口；TMDB 查询等待期间也会复查会员身份与权限。会员删除后，同邮箱新建会员不会取得原会员的申请。尚未到达已入库自动清理期限的历史工单保留供管理员核对，不因同邮箱重新关联。

申请保存于现有 SQLite 的 `media_requests` 表，通过启动迁移后的幂等对账建立表和索引；升级保留历史业务数据，运行时仅按上述已入库保留规则清理。未结束申请另有数据库唯一索引保护；管理员更新与审计在同一事务完成。新建申请有每会员每分钟 30 次的技术限流，重复未结束申请不重复查询 TMDB。

| 方法 | 接口 | 用途 |
| --- | --- | --- |
| GET | `/api/public/media-requests` | 当前会员申请分页，支持 `page`、`pageSize`、`status`、`q` |
| POST | `/api/public/media-requests` | 提交作品、季号与申请说明，重复返回原申请 |
| PATCH | `/api/public/media-requests/:id` | 修改本人未结束申请说明，需提供 `updatedAt` |
| GET | `/api/media-requests` | 管理端按状态、名称或邮箱分页查询 |
| PATCH | `/api/media-requests/:id` | 管理端修改状态、反馈，需提供 `updatedAt` |

TMDB 搜索与资料读取沿用已有配置和接口。未配置、上游失败或资料不完整时保留表单并提示失败，不生成无法确认身份的申请。自动测试和本地夹具不代替真实 TMDB 联调。
